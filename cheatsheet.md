## 1. Три потока
- У команды два выхода: 1 — результат, 2 — сообщения об ошибках. Они работают независимо: команда может писать в один, в другой, в оба сразу или ни в один.
- «>» и 2> — это не команды, а операторы перенаправления.
У каждой команды есть три «трубы»:

Номер	Название	Что это	По умолчанию
0	stdin	вход, откуда команда читает	клавиатура
1	stdout	обычный вывод, результат	экран
2	stderr	ошибки	тоже экран
Обычный вывод и ошибки — два разных потока. На экране они смешиваются, и кажется, что это одно и то же. Но перенаправлять их можно по отдельности. Отсюда и ответ на задание 3.
Аналогия: у команды есть два выхода, «готовая продукция» (1) и «брак» (2). Оба по умолчанию сыплются на один стол, на экран.
- «>» — вывод в файл (с перезаписью)
Вывод не попадает на экран, а записывается в etc.txt. Если файла нет, он создаётся. Если файл был, его содержимое стирается без вопросов. Корзины нет, -i нет.
- «>>» — дописать в конец
То же самое, но старое содержимое остаётся, а новое добавляется в конец.
echo просто выводит текст, который ты ему дал. Вместе с >> им удобно дописывать строки в файл.
Чтобы не путать: один > перезаписывает, два >> добавляют.
- 2> — ошибки в файл
Цифра 2 — это номер потока ошибок. Ошибка уходит в файл, на экране пусто.
Можно разделить оба потока сразу:
Результат попадёт в ok.txt, а ошибка — в err.txt.
Обрати внимание: > — это на самом деле сокращение от 1>.
- /dev/null — «чёрная дыра»
Это специальный файл: всё, что в него пишешь, исчезает.
find по всей системе выдаёт сотни ошибок Permission denied. Если отправить их в /dev/null, на экране останутся только найденные файлы. Это пригодится в среду, когда дойдём до find.
- «|» — конвейер (pipe)
cat /etc/passwd | less
| передаёт вывод одной команды на вход следующей, а не в файл. Первая команда выдаёт текст, вторая его обрабатывает. Промежуточных файлов нет.
	Куда уходит вывод
«>»	в файл
|	в другую команду
На этом держится вся неделя. Скоро будут цепочки вроде:
grep "install" /var/log/dpkg.log | wc -l
Здесь grep находит строки, а wc -l их считает. Это и есть критерий недели: «одной командой нашёл строки в логе и посчитал».
- Ловушки
«>» вместо >> — молча стёр файл.
cat file.txt > file.txt — файл станет пустым. Bash сначала очищает файл для записи и только потом запускает cat, а тому уже нечего читать.
«>» file перехватывает только stdout. Ошибки всё равно вылезут на экран, для них нужен 2>.
## grep и wc
- grep — оставляет только строки, в которых есть нужный текст
Схема:
файл ──► grep 'apple' ──► выход 1: только строки, где есть "apple"
                     └──► выход 2: ошибки (например, нет такого файла)
Важно: grep ищет кусок текста, а не слово целиком. По apple найдётся и pineapple.
Регистр учитывается: apple и Apple для grep разные слова.
Шаблон бери в кавычки '...', особенно если в нём есть пробелы.
Если ничего не нашлось, grep ничего не выводит, и это не ошибка.
Основные ключи:
Ключ	Что делает
- «-i»	не различать большие и маленькие буквы
- «-v»	наоборот: строки, где этого текста нет
- «-n»	показать номер строки
- «-c»	вместо самих строк вывести их количество
- «- wc» — считает строки, слова и символы (word count)
- «-a» считай файл текстом, что бы там ни было
- «-B» = Before, строки до; -A = After, строки после. Нам нужны после. grep -A 3 "Failed with result 'signal'"
- zgrep сам распаковывает файл на лету и ищет внутри для сжатых файлов .gz
Команда	Что считает
wc файл	строки, слова и байты
- wc -l файл	только строки (чаще всего нужно именно это)
- wc -w файл	слова
- wc -c выводит количество байт в указанном файле или в тексте, который передали ей на вход
- wc -l считает строки. файл выводит 5 файл, то есть число и имя. Если данные пришли через |, имени файла нет, выводится просто 5.
Связка через |
wc -l fruits.txt          →  7 fruits.txt
cat fruits.txt | wc -l    →  7
grep 'install' /var/log/dpkg.log | wc -l
   │                               │
   └ оставил нужные строки ──────► └ посчитал их
Это то же самое, что grep -c 'install' /var/log/dpkg.log. Полезно знать оба способа: | wc -l можно поставить после любой команды, а не только после grep.
## sort / uniq / cut и find 
Sort: сортирует строки 
- sort файл     # по алфавиту
- sort -r	    # в обратном порядке (reverse)
- sort -n	    # как числа: 9 < 10. Без -n будет «10» < «9», потому что строки сравниваются по первому символу
uniq: убирает повторы
- Главная ловушка: uniq убирает только одинаковые строки, которые стоят подряд. Поэтому почти всегда пишут sort | uniq: сначала сортировка собирает одинаковые строки вместе.
- uniq -c пишет перед строкой, сколько раз она встретилась (count).
Связка, которую надо запомнить: sort | uniq -c | sort -rn выдаёт рейтинг «что встречается чаще всего».
Строка 1 USER — это не пользователь, а заголовок колонки. ps всегда печатает его первой строкой, а sort | uniq -c посчитал его как ещё одно значение. По той же причине в 113 одна строка лишняя, так что процессов на самом деле 112. Убрать заголовок можно знаком = после имени колонки:
ps -eo user= | sort | uniq -c | sort -rn
- sort + uniq -u (строки без повторов)
cut: вырезает колонку
- cut -d: -f1 файл означает «разделитель :, взять поле 1». Пробел как разделитель пишется в кавычках: -d' '
- «-d» — разделитель (delimiter), -f — номер поля (field), можно перечислить: -f1,7.
Удобно на /etc/passwd, где поля разделены :: alex:x:1000:1000:alex:/home/alex:/bin/bash
 	                                          1   2  3    4    5      6          7
find: ищет файлы по имени и типу
- find ГДЕ  -name "ЧТО"    может быть ещё -type f (файлы) d (директории) без find ищет всё подряд
- find ~/study -name "*.txt" — все .txt внутри ~/study, включая подпапки. Шаблон бери в кавычки, иначе bash сам подставит вместо * имена файлов из текущей папки (* Звёздочка значит «что угодно». ).
- «-iname» — то же самое, но без учёта регистра.
- «-type f» — только файлы, -type d — только папки.
- «-size 1033c» размер ровно 1033 байта. c = байты: без буквы find считает в блоках по 512 байт, и ничего не найдётся

- «!» «НЕ», переворачивает следующее условие. ! -executable = права

Чем find отличается от grep: grep ищет текст внутри файлов, а find ищет файлы по имени. Во вторник ты столкнулся с этим, когда grep 'ssh' /usr/bin выдал «Is a directory».

Ловушки
- useradd без -m и -s создаст пользователя без домашней папки и с /bin/sh. Ключи обязательны. (Есть ещё adduser, он задаёт вопросы и делает всё сам, но на собеседованиях и в скриптах встречается useradd.)
- ⚠️ usermod -G без -a не добавляет группу, а заменяет весь список групп. Если сделать так с alex, он вылетит из группы sudo и потеряет права администратора. Всегда пиши -aG (a = append, «дописать»), и с alex сегодня ничего не делаем.
- Значение идёт сразу за своим ключом, как в среду: -s /bin/bash, -G devs. В -aG devs значение devs относится к G, поэтому G стоит последней.
- Новая группа начинает работать только после нового входа пользователя (su - bob заново).
- Пароль при вводе не отображается, даже звёздочками. Это нормально.
Контрольные вопросы
1 Где хранятся пароли и почему не в /etc/passwd?
  В /etc/shadow, который может читать только root. /etc/passwd открыт всем, потому что его читают многие программы, например чтобы показать имя владельца файла в ls -l.
2 Чем usermod -G devs bob опасно отличается от usermod -aG devs bob?
  Без -a список групп bob заменится на одну devs, и все остальные его группы пропадут. С -a devs добавится к уже имеющимся.
3 Что значит /usr/sbin/nologin в 7-м поле?
  Служебный пользователь, под ним нельзя войти в систему.
4 Какой пароль спрашивает sudo, а какой su - bob?
  sudo спрашивает пароль того, кто вводит команду (твой). su - bob спрашивает пароль bob.
5 Что сделает sudo useradd bob без ключей и чем это плохо?
  Создаст пользователя без домашней папки и с /bin/sh. Войти под ним будет неудобно, и своих файлов ему хранить негде.
## права доступа (rwx, chmod, chown)
-rw-r--r--  1  root  root  2345  ноя 11  /etc/passwd
│└┬┘└┬┘└┬┘     └┬─┘  └┬─┘
│ │  │  │       │     └─ группа файла
│ │  │  │       └─────── владелец файла
│ │  │  └─ o (others): все остальные
│ │  └──── g (group): участники группы файла
│ └─────── u (user): владелец
└───────── тип: - файл, d папка
Девять символов делятся на три тройки: владелец, группа, остальные. Каждая тройка всегда идёт в порядке r w x, а - на месте буквы значит «этого права нет».

- r (read)    для файла: читать содержимое (cat)    для папки:   видеть список имён (ls)
- w (write)   для файла: менять содержимое (>>, редактор)    для папки:   создавать, удалять и переименовывать файлы внутри
- x (execute)   для файла: запускать как программу (./script.sh)    для папки:   входить (cd) и обращаться к файлам внутри
 ⚠️ Удалить файл можно или нельзя в зависимости от прав на папку (w), а не на сам файл.

Какую тройку проверяет система
Ты владелец файла?   ──да──► берётся ТОЛЬКО тройка u
        │нет
Ты в группе файла?   ──да──► берётся ТОЛЬКО тройка g
        │нет
        └──────────────────► тройка o
 Проверка останавливается на первом совпадении. root ограничений не имеет.
 
 chmod буквами
 Схема: chmod КОМУ ДЕЙСТВИЕ ПРАВА файл
кому: u владелец, g группа, o остальные, a все
действие: + добавить, - убрать, = установить ровно так
- chmod u+x script.sh        владельцу добавить x
- chmod o-r notes.txt        остальным убрать r
- chmod g=rw notes.txt       группе ровно rw
- chmod u=rwx,g=rx,o= f      сразу все три тройки (o= значит «ничего»)
Буквы «кому» можно писать вместе: chmod ug+x backup.sh  Ещё вариант через запятую: chmod u+x,g+x backup.sh.

chmod = mode, режим, то есть права (700, u+x)
chown = owner, владелец, то есть кто (dana:dana)

   chmod числами
Каждое право имеет вес: r = 4, w = 2, x = 1. Веса в тройке складываются, получается одна цифра на тройку.
rwx = 4+2+1 = 7      r-x = 4+0+1 = 5      rw- = 4+2+0 = 6
r-- = 4              --- = 0
число	права	   где встречается
755	  rwxr-xr-x	   папки, скрипты
644   rw-r--r--	   обычные файлы
700	  rwx------	   личная папка
600	  rw-------	   секретный файл (ключи)
750	  rwxr-x---	   домашние папки в Ubuntu 26
Проверить себя числом: stat -c '%a %A %U %G' файл покажет, например, 644 -rw-r--r-- alex alex.

chown: сменить владельца или группу
- sudo chown bob file            владелец bob
- sudo chown bob:devs file       владелец bob, группа devs
- sudo chown :devs file          только группа
- sudo chown -R bob:devs dir     то же для папки со всем содержимым
Отдать файл другому может только root, поэтому chown всегда идёт через sudo. А chmod для своего файла работает без sudo.

Ещё два инструмента на сегодня
- ls -ld папка показывает права самой папки. Без -d команда покажет её содержимое.
- sudo -u bob КОМАНДА выполняет одну команду от имени bob без входа в его сессию. Это удобно, чтобы проверить, что видит другой пользователь.

Ловушки сегодняшнего дня
- Порядок аргументов: chmod ПРАВА ФАЙЛ и chown КТО ФАЙЛ. Сначала права или владелец, потом файл.
- chmod 644 на папку убирает x у всех, и войти в неё больше нельзя.
- sudo только приставка, за ней идёт команда целиком: sudo chown ..., а не sudo bob ....

## 1. Программа и процесс — разные вещи
Программа — это файл на диске: /usr/bin/sleep. Он просто лежит.
Процесс — это запущенная копия программы. Можно запустить sleep три раза, и будет 1 файл и 3 процесса.
У каждого процесса есть:
Что      Что значит
PID      номер процесса, уникальный
PPID     PID родителя (кто его запустил). Команду в терминале запускает bash, значит родитель — bash
USER     владелец процесса — от чьего имени он работает
STAT     состояние: R работает, S спит/ждёт, T остановлен, Z зомби
PID 1 — это systemd, прародитель всех процессов (с ним будем работать завтра).
echo $$ — показать PID твоего текущего bash.

ps — R+: Running, прямо сейчас работает на переднем плане (ведь это он делает снимок);
bash — Ss: спит в ожидании твоей команды, а маленькая s значит «главный процесс сессии» (твоего SSH-входа).
T (sTopped) — заморожен, ничего не делает
S (Sleeping) — работает, но спит в ожидании
## 2. Смотреть процессы: ps и pgrep

## 4. Сигналы и kill
kill не убивает, а отправляет сигнал. Что делать с сигналом, решает процесс (кроме 9 и 19).
№     Имя    Что делает                                                     Как отправить

pkill sleep        # TERM всем процессам по ИМЕНИ
kill -l            # список всех сигналов

Почему не начинать с -9: процесс не успеет сохранить данные и удалить временные файлы. Порядок: kill → подождать → проверить pgrep → только потом kill -9.

## Службы и systemctl
### Что такое служба

Служба (демон) — это программа, которая работает в фоне всё время, без терминала и без тебя. Примеры: sshd принимает SSH-подключения, cron запускает задачи по расписанию, nginx отдаёт сайт (он будет в субботу).

По сути служба — это обычный процесс, как твой sleep 900 &. Разница в том, кто её запускает и присматривает за ней. Это делаешь не ты, а systemd.

systemd — это первый процесс в системе (PID 1). Ты видел его сегодня в top: строка 1 root ... systemd. Ядро запускает его первым, а дальше он запускает всё остальное и следит за службами.

### Карта видов объектов 
Что                                    Вид объекта                                Пример
systemctl                              команда, ею управляют службами             systemctl status cron
cron.service                           юнит, то есть имя службы для systemd
/usr/lib/systemd/system/cron.service   файл юнита, описание: что запускать и как
/usr/sbin/cron                         файл программы
cron с PID 812                         процесс, то есть запущенная программа       ps -p 812
Цепочка такая: команда systemctl → говорит systemd → systemd читает файл юнита → запускает программу → появляется процесс.
Где лежат файлы юнитов:
/usr/lib/systemd/system/ — их ставят пакеты, руками там не правят;
/etc/systemd/system/ — сюда пишет администратор (то есть ты), и эти файлы главнее.
- systemctl cat cron   Посмотреть файл юнита

### Типы юнитов (по окончанию имени)
.service — служба, то есть программа, которую надо держать запущенной. Это 90% того, что ты будешь трогать.
.socket — «слушает порт и будит службу, когда пришло подключение». Это твой случай с ssh.socket с 06.11.
.timer — запуск по расписанию, современная замена cron.
.target — группа юнитов, «этап загрузки».
Окончание .service можно не писать: systemctl status cron = systemctl status cron.service. Для остальных типов окончание пишется обязательно: systemctl status ssh.socket.

### Главное: два независимых переключателя
               Что меняет                                 Команды
СЕЙЧАС         работает служба или нет в данный момент    start, stop, restart
ПРИ ЗАГРУЗКЕ   запустится ли она сама после перезагрузки  enable, disable
enabled не значит «работает». Это значит «включена в автозагрузку»

Эти переключатели не связаны друг с другом. Отсюда две классические ловушки:
stop без disable: служба остановлена, но после перезагрузки снова работает.
enable без start: служба «включена», но сейчас не работает, до перезагрузки.
Оба действия сразу: enable --now (включить и запустить) и disable --now (выключить и остановить).
enable       → при загрузке ВМ   (будущее)
start        → прямо сейчас      (настоящее)

                 СЕЙЧАС (active)      ПРИ ЗАГРУЗКЕ (enabled)
start / stop  →  меняет               не трогает
enable/disable→  не трогает           меняет

enable --now → и то и другое
Все команды:
systemctl status ИМЯ           # посмотреть (sudo не нужен) (можно проверить, существует ли служба)
sudo systemctl start ИМЯ       # запустить сейчас
sudo systemctl stop ИМЯ        # остановить сейчас
sudo systemctl restart ИМЯ     # остановить и запустить заново (новый PID!)
sudo systemctl reload ИМЯ      # перечитать настройки без остановки (не все службы умеют)
sudo systemctl enable ИМЯ      # запускать при загрузке
sudo systemctl disable ИМЯ     # не запускать при загрузке
systemctl is-active ИМЯ        # одно слово: active / inactive / failed
systemctl is-enabled ИМЯ       # одно слово: enabled / disabled
systemctl list-units --type=service --state=running   # что сейчас работает
sudo systemctl enable --now ИМЯ # запускает и то и то

Про sudo: смотреть (status, is-active, cat, list-units) можно без него, а менять (start, stop, enable...) — только через sudo. Если забудешь sudo, systemctl спросит пароль сам или откажет.
sudo systemctl ...: sudo — приставка, за ней идёт обычная команда целиком. Не sudo start cron, а sudo systemctl start cron.

### Ловушка с SSH
Ты подключён к ВМ по SSH. Не останавливай ssh и ssh.socket, иначе отрежешь себе вход: новые подключения перестанут приниматься, и придётся лезть в окно VirtualBox.
Почему ssh.service может быть inactive, хотя ты подключён: порт 22 держит ssh.socket и будит sshd, когда приходит подключение. Ты разбирал это 06.11.
Практиковаться будем на cron. Он безопасен: если его остановить на 5 минут, ничего не сломается.
ssh.socket  (active)    ← systemd сам держит порт 22 и ждёт
     │  пришло подключение
     ▼
ssh.service (запускается только на время подключения)
Это называется сокет-активация. В покое ssh.service выглядит как inactive, но порт открыт, потому что его держит systemd через юнит ssh.socket. Проверить можно так: systemctl is-active ssh.socket
загрузка ВМ
   └─ ssh.socket (enabled → стартует при загрузке) → systemd держит порт 22
         └─ первое подключение → systemd запускает ssh.service → он работает дальше
• ssh.service disabled: своя автозагрузка ему не нужна, его запускает сокет. Если бы он был enabled, sshd стартовал бы при загрузке сам, и сокет-активация потеряла бы смысл.
• ssh.service active: ты подключён, значит, сокет его уже разбудил. 6 ноября ты смотрел status до подключения по SSH, с консоли ВМ, поэтому было inactive.

## журналы (journalctl и /var/log)
### Зачем это нужно
Когда что-то сломалось, DevOps первым делом смотрит журналы (логи). Это записи о событиях: служба запустилась, упала, кто-то вошёл по SSH, ввёл неверный пароль, поставил пакет.

Где                               Кто пишет                                    Формат                           Чем читать
Журнал systemd (служба journald)  всё, что запущено через systemd, плюс ядро   двоичный, через cat не прочитать только journalctl
Папка /var/log    сами программы (dpkg, apt, nginx) или служба rsyslog   обычный текст   less, tail, grep, всё, что ты уже знаешь

Ты их уже видел: нижние строки в systemctl status cron (Started, Failed with result 'signal', Running @reboot jobs) — это кусок журнала. И dpkg.log с прошлой недели, в котором ты считал install, — тоже журнал
Два места, где лежат журналы
                    события (службы, ядро, sudo, ssh...)
                                │
                                ▼
                 systemd-journald  ← служба-сборщик
                     │                    │
        ┌────────────┘                    └──────────────┐
        ▼                                                ▼
 /var/log/journal/                              rsyslog (если стоит)
 двоичный формат, читать                         пишет копию текстом:
 ТОЛЬКО через journalctl                         /var/log/syslog, auth.log...

 + программы, которые пишут свои файлы сами:
   /var/log/dpkg.log, /var/log/apt/, позже nginx: /var/log/nginx/
- journald собирает всё в одно место. Его файлы двоичные: cat по ним выдаст мусор, читать их можно только через journalctl.
- /var/log — обычные текстовые файлы. Читаются уже знакомыми инструментами: less, tail, grep, cut.

### Как читать одну строку
Nov 17 13:04:37 ubuntoserver cron[1619]: (CRON) INFO (Running @reboot jobs)
└─── время ───┘ └── хост ──┘ └─процесс[PID]┘ └──────── сообщение ────────┘
Время на ВМ в UTC (в status было 13:04:37 UTC). Оно отличается от твоего местного, это нормально для серверов.

### journalctl: основные ключи
Команда                          Что делает
journalctl                       весь журнал, старые сверху, открывается в less
journalctl -e                    сразу в конец (свежее)
journalctl -r                    в обратном порядке: свежие сверху
journalctl -n 20                 последние 20 строк
journalctl -u cron               только юнит cron (u = unit)
journalctl -f                    следить в реальном времени (как tail -f), выход — Ctrl+C
journalctl -b                    только с последней загрузки (b = boot)
journalctl -b -1                 предыдущая загрузка
journalctl --list-boots          список загрузок 
journalctl --since "1 hour ago"  за последний час; также today, "2026-11-17 13:00"  
--since "1 hour ago", --since today, --since yesterday, --since "2026-11-17 20:00", --until ...    фильтр по времени
journalctl -u ИМЯ --since "ГГГГ-ММ-ДД ЧЧ:ММ"
journalctl -p err                только ошибки и серьёзнее
journalctl -k                    только сообщения ядра
journalctl --no-pager            без less, просто вывод (удобно для | grep)
journalctl --disk-usage          сколько места занимает журнал (мостик к пятнице)
Ключи складываются:    journalctl -u cron -b -n 20   (Это «последние 20 строк cron с текущей загрузки».)
С grep тоже работает: journalctl -u cron | grep reboot. Если вывод идёт в |, less не открывается.
Важность (-p). У каждой записи есть уровень, от 0 до 7:
0 emerg  1 alert  2 crit  3 err  4 warning  5 notice  6 info  7 debug
└──────── всё плохо ────────┘    └ предупр. ┘  └──── обычное ────┘
-p err = уровень 3 и все серьёзнее (0–3). -p warning = 0–4.
Всего уровней 8, от самого страшного к самому мелкому:
0 emerg → 1 alert → 2 crit → 3 err → 4 warning → 5 notice → 6 info → 7 debug
-p err показывает уровни 0–3, -p warning показывает 0–4. Чем ниже ты опускаешь планку, тем больше строк. В выводе err подсвечиваются красным, warning жёлтым (то же жёлтое, что было у EXTRA_OPTS).

## apt и dpkg
### Пакет, репозиторий, зависимости
• Пакет — архив .deb с программой: её файлы, куда их положить и что ей нужно для работы.
• Репозиторий — сервер Ubuntu, где лежат тысячи пакетов. Список репозиториев на ВМ: /etc/apt/sources.list.d/ubuntu.sources.
• Зависимости — другие пакеты, без которых этот не работает. Ставишь один пакет, и следом подтягиваются ещё несколько.
### Два уровня: dpkg и apt
                        dpkg (нижний уровень)                  apt (верхний уровень)
Что делает  ставит и удаляет .deb, который уже лежит на диске  сам скачивает из репозитория, решает зависимости, потом вызывает dpkg        не решает, просто ругается                          решает сам
Зависимости  /var/log/dpkg.log (что сделали с пакетом)          /var/log/apt/history.log (кто и какой командой)
Это объясняет то, что ты сегодня видел у sos: apt (unattended-upgrade) скачал пакет, а dpkg записал каждый шаг установки.

### Команды apt
Привычка на будущее: прежде чем ставить незнакомый пакет, загляни в apt show. Две секунды — и ясно, что это такое и откуда.

Команда                           Что делает

apt list --upgradable             что можно обновить

sudo apt install ИМЯ              ставит пакет вместе с зависимостями (-y — не спрашивать «Да/Нет»)
sudo apt remove ИМЯ               удаляет программу, настройки в /etc остаются

sudo apt autoremove               убирает зависимости, которые больше никому не нужны
apt search СЛОВО                  ищет пакет по названию и описанию

Порядок всегда такой: сначала update, потом install или upgrade.

Команда                 Что делает

• ii — установлен, всё в порядке;
• rc — удалён через remove, но настройки остались. После purge строка исчезает.

command-not-found предлагает apt install ...: сначала проверь, что ты не опечатался. Вспомни историю с systemcrl и пакетом systemctl.
Служба после установки сразу работает. В Debian и Ubuntu пакет со службой при установке делает её enabled + active. В субботу проверишь на nginx через systemctl.

## диски и память
### Четыре слоя: от железа до папки
Сначала главная схема, на ней держится вся тема:
диск (железо)  →  раздел (кусок диска)  →  файловая система (порядок внутри)  →  точка монтирования (в точке монтирования: в папку подключается не программа, а файловая система.)
   sda               sda2                        ext4                                /boot
в точке монтирования: в папку подключается не программа, а файловая система. Программы лежат внутри неё как файлы. Опять путаются виды объектов (программа ↔ файловая система).
   
• Диск — устройство целиком. В Linux он выглядит как файл в /dev: /dev/sda — первый диск (у тебя виртуальный, 20 ГБ).
• Раздел — кусок диска: sda1, sda2, sda3. Цифра — номер раздела.
• Файловая система (ext4, xfs) — способ разметить раздел так, чтобы в нём хранились файлы и папки. Пустой раздел без неё — просто байты.
• Точка монтирования — папка, к которой подключена файловая система. Помнишь «одно дерево от /» из недели 1? Вот как оно собирается: разные разделы подключаются в разные папки этого дерева. Буквы диска, как в Windows (C:, D:), здесь нет.

### LVM: прослойка у тебя на ВМ
При установке ты выбрал LVM. Он добавляет гибкий слой между разделом и файловой системой:
sda3 (раздел)  →  PV  →  VG ubuntu-vg (общий «бак»)  →  LV ubuntu-lv (выданный кусок)  →  ext4  →  /
• PV (physical volume) — раздел, отданный под LVM;
• VG (volume group) — общий запас места из одного или нескольких PV;
• LV (logical volume) — кусок из этого запаса, на нём уже файловая система.
Зачем это нужно: LV можно увеличить на ходу, не переразмечая диск. У тебя под / выдано 10 ГБ, а в ubuntu-vg ещё 8,6 ГБ свободно. Установщик Ubuntu специально оставляет запас. Увеличивать будем позже, отдельным упражнением.

В системе LV называется /dev/mapper/ubuntu--vg-ubuntu--lv. Двойной дефис — не опечатка, так LVM экранирует дефис внутри имени.

### lsblk: что подключено
lsblk
Показывает дерево устройств. У тебя будет примерно так:
NAME                      SIZE TYPE MOUNTPOINTS
sda                        20G disk
├─sda1                      1M part
├─sda2                      2G part /boot
└─sda3                     18G part
  └─ubuntu--vg-ubuntu--lv  10G lvm  /
sr0                      1024M rom
• TYPE: disk — диск, part — раздел, lvm — логический том, rom — виртуальный CD-привод;
• MOUNTPOINTS — куда подключено; пусто = никуда;
• здесь сразу видно, что sda3 занимает 18 ГБ, а LV на нём только 10: остальное — тот самый запас.
Полезные варианты: lsblk -f (тип файловой системы), sudo vgs (сколько свободно в VG, колонка VFree).

### df -h: сколько места на файловых системах
sudo vgs
df -h
df = disk free. Показывает подключённые файловые системы и их заполненность:
Filesystem                         Size  Used Avail Use% Mounted on
/dev/mapper/ubuntu--vg-ubuntu--lv  9.8G  4.9G  4.4G  53% /
/dev/sda2                          1.9G  200M  1.6G  11% /boot
tmpfs                              ...                   /run

Ответ на «что занимает место в /var» — du:
sudo du -h --max-depth=1 /var | sort -h
Правило: df — сколько занято всего, du — кто занял.

• главное — Use% и Mounted on: «на / занято 53%»;
• -h = human: размеры в K/M/G, а не в блоках по 1 КБ;
• tmpfs — файловая система в оперативной памяти, а не на диске (/run, /dev/shm). После перезагрузки она очищается. Поэтому метка cron /run/crond.reboot и пропадала при reboot (вторник);
• df -h /var/log — показать только ту файловую систему, на которой лежит эта папка.
На работе df -h — первая команда, когда «сервер упал / не пишет логи / база не стартует». Диск заполнен на 100% — частая причина.

### du -sh: сколько весит папка
df отвечает «сколько занято всего», du — «кто занял». du = disk usage.
du -sh ~/study
• -s = summary: одно итоговое число, а не каждая вложенная папка (без -s вывод зальёт экран);
• -h = в K/M/G.
Главный рецепт: что занимает место внутри папки, с сортировкой:
sudo du -h --max-depth=1 /var | sort -h
• --max-depth=1 — только папки первого уровня;
• sort -h — сортировка человеческих размеров (понимает, что 2G > 900M). Обычный sort -n здесь соврёт: для него 900 больше 2;
• sudo — в системных папках есть закрытые подпапки, без sudo будут Permission denied (или добавь 2>/dev/null, как в find).
Дальше идёшь вглубь: самая тяжёлая оказалась /var/log → запускаешь то же самое на /var/log и так далее, пока не найдёшь виновника.

df говорит, что место кончается → du --max-depth=1 | sort -h → заходишь в лидера → повторяешь, пока не найдёшь виновника.

ls -lh показывает размер файла. Размер папки в ls -l (обычно 4.0K) — это размер самой записи о папке, а не её содержимого. Вес содержимого папки — только через du. Это снова граница «файл ↔ папка».

Шпаргалка «кончается место»: df -h → du ... | sort -h → apt clean, journalctl --vacuum-size, apt autoremove.

### free -h: оперативная память
free -h
               total   used   free  shared  buff/cache  available
Mem:           1.9Gi   300Mi  1.1Gi   ...      600Mi       1.6Gi
Swap:          2.0Gi     0B   2.0Gi
• available — сколько памяти реально можно отдать программам. Смотреть надо сюда;
• free — память, которая вообще ничем не занята. Её часто мало, и это нормально;
• buff/cache — Linux складывает в свободную память кэш недавно прочитанных файлов, чтобы второй раз читать быстрее. Как только память понадобится программе, кэш освобождается. Поэтому available ≈ free + большая часть buff/cache;
• Swap — подкачка: кусок диска, куда система выгружает память, когда оперативная кончается. Диск в сотни раз медленнее памяти, поэтому, если swap активно используется, сервер тормозит. У тебя в htop было Swp 0K — подкачка не нужна.
Это те же цифры, что полоска Mem в htop, только в таблице.

Как читать строку Mem:
total 1.6Gi = used 364Mi + free 999Mi + buff/cache 422Mi (примерно)
available 1.2Gi ≈ free + та часть кэша, которую ядро отдаст по первому требованию
• free — память, которая вообще ничем не занята.
• buff/cache — ядро держит здесь недавно прочитанные с диска файлы, чтобы второй раз читать быстрее. Это не «занято навсегда»: если программе понадобится память, кэш выкидывается.
• available — сколько реально можно отдать новым программам. Смотреть надо на эту колонку. Если free маленький, а available большой, всё в порядке: Linux просто использует свободную память под кэш.
Swap: 1.6Gi, занято 0B. Память не кончалась, ни один процесс не выталкивался на диск. Тревожный признак — когда swap used растёт, а available близок к нулю.

Мостик к следующему заданию: /swap.img — обычный файл на /. Значит, его 1.6G входят в те 5.3G Used из df. Почти треть занятого места на корне — это swap.

### Ловушки
• df говорит «диск полон», а du не находит, чем. Файл удалили через rm, но процесс (например, служба, которая писала в этот лог) всё ещё держит его открытым. Имя файла исчезло, а место не освободилось. Лечится перезапуском той службы: systemctl restart, как во вторник.
• Диск 20 ГБ, а df показывает 10. Это не ошибка: LV выдан не на всё место, остальное лежит в VG (sudo vgs).
• «Свободной памяти почти нет!» Смотри available, а не free. Кэш — не утечка.
 • Один ключ — разный смысл (опять): -h у df/du/free = «человеческие» размеры, а у sort -h = сортировка таких размеров. Это не --help. Та же история, что grep -c и wc -c.
• du -sh * не видит скрытые файлы (.cache и т. п.), потому что * не подставляет имена с точкой. Для домашней папки лучше du -h --max-depth=1 ~ | sort -h.

### Как это связано с прошлыми днями
• journalctl --disk-usage — сколько места занимает журнал (бонус среды, который ты не делал);
• /var/cache/apt/archives — сюда apt складывает скачанные .deb; sudo apt clean их удаляет;
• /var/log с архивами .gz — logrotate как раз следит, чтобы логи не съели диск.

### Схема
диск → раздел → (LVM: PV → VG → LV) → файловая система → точка монтирования
пример с ВМ: sda → sda3 → ubuntu-vg → ubuntu-lv → ext4 → /

### Что есть и как устроено
| Команда             | Что делает |
| `lsblk`             | дерево устройств: диски, разделы, LVM, куда смонтировано. loop = snap-пакеты, sr0 = CD-привод |
| `lsblk -f`          | то же + тип ФС и UUID |
| `df -h`             | файловые системы: Size / Used / Avail / Use%. `-h` = в K/M/G |
| `df -hT`            | + колонка Type (ext4, tmpfs) |
| `df -h /`           | только корень |
| `df -i`             | inode (кол-во файлов); бывает «места нет», хотя Use% мало |
| `findmnt`           | что куда смонтировано, деревом |
| `mount \| grep sda` | то же, по-старому |
| `cat /etc/fstab`    | что монтируется при загрузке |

- tmpfs — в оперативке, на диске 0. В 26.04 `/tmp` тоже tmpfs (стирается при reboot).
- ext4 держит 5% в резерве для root → Used + Avail < Size.
- Тревожно: Use% выше 80–90%.

### LVM
| Команда | Что делает |
|---|---|
| `sudo pvs` | PV — разделы, отданные под LVM (PSize, PFree) |
| `sudo vgs` | VG — общий котёл. **VFree = свободно в котле**, df его не видит |
| `sudo lvs` | LV — тома, нарезанные из котла (LSize) |
| `sudo lvextend -r -L +4G /dev/ubuntu-vg/ubuntu-lv` | увеличить том на 4G **вместе с ФС** (`-r`), на ходу, без перезагрузки |
| `sudo lvextend -r -l +100%FREE /dev/ubuntu-vg/ubuntu-lv` | отдать всё свободное (лучше порциями) |

- Без `-r`: LV вырастет, а ФС и df — нет.
- ext4 увеличивать на ходу можно, уменьшать — нельзя.

### Кто ест место
| Команда | Что делает |
|---|---|
| `du -sh папка` | сколько весит папка целиком (`-s` итог, `-h` в K/M/G) |
| `sudo du -h --max-depth=1 /var \| sort -h` | вес каждой подпапки, большие внизу |
| `... \| sort -h \| tail -n 5` | только лидеры |
| `sudo du -h --max-depth=1 -x / \| sort -h` | весь корень, `-x` = не лезть в другие ФС (/proc, tmpfs, /boot) |
| `du -sh *` | вес всего в текущей папке |
| `ls -lhS` | файлы в папке по размеру, большие сверху |
| `sudo find / -xdev -type f -size +100M 2>/dev/null` | все файлы больше 100M |

Метод: `df -h` → `du --max-depth=1 | sort -h` → зайти в лидера → повторить.
du видит только папки в списке; файлы в самой папке входят только в итог (пример: `/swap.img`).

### Чистка
| Команда | Что делает |
|---|---|

| `sudo apt autoremove` | удалить ненужные зависимости |

### Ловушка df ≠ du
`rm` удаляет имя файла, а данные держит процесс, у которого файл открыт.
du не видит (имени нет), df видит (блоки заняты).
| Команда | Что делает |
|---|---|
| `ls -l /proc/PID/fd` | открытые файлы процесса, ищи `(deleted)` |
| `sudo lsof +L1` | все удалённые, но открытые файлы (если lsof установлен) |
| `kill PID` / `sudo systemctl restart служба` | отпустить файл → место вернётся |

### Память
| Команда | Что делает |
|---|---|
| `free -h` | память: used / free / buff/cache / **available** |
| `swapon --show` | swap: файл или раздел, сколько занято |
| `ls -lh /swap.img` | swap-файл лежит на `/` и ест место |

- Смотреть на **available**, а не на free. buff/cache — кэш файлов, отдаётся по требованию.
- Тревожно: available около 0 и растёт used у swap.

### Для тестов
| Команда | Что делает |
|---|---|
| `fallocate -l 1G big.img` | мгновенно создать файл на 1G (блоки резервируются) |
| `dd if=/dev/zero of=big.img bs=1M count=300` | реально записать 300M (идёт через кэш) |

### Ловушки
- `-h` у df/du/free = «в K/M/G», а у `sort -h` = «сортировать такие числа».
- lsblk показывает размер тома, df — размер ФС на нём (10G против 9.8G).
- 10G из 20G — это не ошибка, остальное лежит в VFree.

## nginx
Nginx («энджин-экс») — это программа, которая принимает HTTP-запросы и отвечает на них. В нашей практике она работала как веб-сервер: у тебя на Ubuntu-ВМ лежала готовая HTML-страница, а nginx отдавал её по запросу.

— systemctl status nginx показывает текущее состояние службы.
— journalctl -u nginx помогает разобраться, когда служба запускалась и останавливалась и были ли ошибки запуска.
/var/log/nginx/access.log хранит записи об HTTP-запросах, а /var/log/nginx/error.log — ошибки, которые nginx пишет в свой лог.

| Что хочешь узнать                               | Где смотреть |
| Запущена ли служба сейчас                       | `systemctl is-active nginx` |
| Настроен ли запуск службы при загрузке ВМ       | `systemctl is-enabled nginx` |
| Какой процесс слушает порт 80                   | `sudo ss -ltnp 'sport = :80'` |
| Что происходило при запуске и остановке службы  | `journalctl -u nginx -n 20` |
| Какой запрос пришёл и какой код вернул nginx    | `sudo tail /var/log/nginx/access.log` |

###  Как это связано с systemctl и логами
| Что ты использовал          | Что оно делает |
| `systemctl`                 | Управляет службой nginx. Через него ты попросил систему остановить и снова запустить nginx. |
| `curl`                      | Играет роль клиента. Подключается к серверу, отправляет запрос и показывает результат. |
| `journalctl -u nginx`       | Показывает события службы. Именно там ты увидел `Stopped nginx.service`. |
| `/var/log/nginx/access.log` | Показывает запросы, которые nginx обработал. Именно там ты увидел `HEAD /` и `200`. |

### Вот шпаргалка для curl -i http://localhost/....
Если вывод начинается с HTTP/1.1 и трёхзначного кода, сервер прислал HTTP-ответ. Если видишь только curl: (7) или другую ошибку curl, смотри, на каком этапе возникла проблема.

HTTP-ответы
| Что увидишь                           | Что это значит |
| **`200 OK`**                          | Запрос выполнен. На твоей ВМ nginx вернул главную страницу. |
| `301 Moved Permanently` / `302 Found` | Сервер предлагает перейти по другому URL. Новый адрес указан в заголовке `Location`. |
| `400 Bad Request`                     | Сервер не смог обработать запрос из-за его формата или содержимого. |
| `401 Unauthorized`                    | Для доступа нужно войти или предоставить действительные учётные данные. |
| `403 Forbidden`                       | Сервер отказал в доступе. Например, nginx не может прочитать файл из-за прав. |
| **`404 Not Found`**                   | Сервер ответил, что ресурс по этому пути не найден. Это твой запрос к `/no-such-page-123`. |
| `500 Internal Server Error`           | При обработке запроса произошла внутренняя ошибка на стороне сервера или приложения. |
| `502 Bad Gateway`                     | Nginx работает как прокси и не получил корректный ответ от приложения. Например, приложение остановилось. |
| `503 Service Unavailable`             | Сервис временно не может обработать запрос. Возможные причины — перегрузка или обслуживание. |
| `504 Gateway Timeout`                 | Nginx работает как прокси и не дождался ответа от приложения вовремя. |

Ошибки curl до получения HTTP-ответа
| Что увидишь                          | Что это значит |
| `curl: (6) Could not resolve host`   | Не удалось узнать IP-адрес по имени хоста. Проверь написание имени и DNS. |
| **`curl: (7) Failed to connect`**    | Не удалось подключиться к адресу и порту. На твоей ВМ это произошло после `systemctl stop nginx`. Ещё одна возможная причина — выбран неверный порт. |
| `curl: (28) Operation timed out`     | Истекло время ожидания. По полному сообщению можно понять, на каком этапе это произошло. |
| `curl: (60) SSL certificate problem` | При HTTPS-запросе `curl` не смог подтвердить подлинность сертификата сервера. |

• curl -I отправляет запрос методом HEAD и показывает заголовки ответа. HTTP-код ищи в первой строке вывода.
• localhost — твоя Ubuntu Server, с которой ты запускаешь команды.
• sudo tail -n 10 читает последние 10 строк журнала. Найди две свежие записи по путям / и /no-such-page-123. В каждой записи метод стоит перед путём, а код ответа — после закрывающей кавычки запроса.

## Текст, байты и файлы
### ROT13 меняет буквы по правилу
ROT13 сдвигает каждую английскую букву на 13 позиций. A превращается в N, а N — обратно в A. Поскольку в английском алфавите 26 букв, одна и та же команда кодирует и декодирует текст. Цифры и знаки препинания остаются прежними.
printf '%s\n' 'Uryyb, QriBcf 123!' | tr 'A-Za-z' 'N-ZA-Mn-za-m'
Результат — Hello, DevOps 123!. Здесь printf передаёт строку в стандартный вывод, | направляет её на стандартный ввод tr, а tr заменяет символы по указанному соответствию.

1. Выведи исходную строку
printf '%s\n' 'Yvahk 123!'
- printf выводит текст.
- '%s\n' говорит, как его вывести. %s — подставить строку, \n — перейти на новую строку.
- 'Yvahk 123!' — сама строка. Кавычки позволяют передать её целиком, вместе с пробелом.
В терминале появится Yvahk 123!.

Передай строку в tr
printf '%s\n' 'Yvahk 123!' | tr 'A-Za-z' 'N-ZA-Mn-za-m'
- | передаёт вывод команды слева на вход команды справа. Теперь строка из printf поступает в tr.
- tr заменяет символы. Первый аргумент, 'A-Za-z', задаёт английские буквы от A до Z и от a до z.
- Второй аргумент, 'N-ZA-Mn-za-m', задаёт те же буквы в сдвинутом порядке. Для заглавных это сначала N–`Z`, затем A–`M`. Символы сопоставляются по позиции, поэтому A превращается в N, B — в O, а N — в A. Строчные работают так же.
Ожидаемый вывод — Linux 123!. Цифры и ! сохранятся, потому что их нет в первом аргументе tr.

### Hex-дамп показывает байты в текстовом виде
Буква A записывается байтом со значением 41 в шестнадцатеричной системе. Буква B — 42. Команда ниже превращает 4142 обратно в байты и выводит AB.
printf '%s' '4142' | xxd -r -p
-r выполняет обратное преобразование, а -p указывает на простой шестнадцатеричный текст без адресов строк. Если дамп создан обычной командой xxd и содержит адреса слева, для восстановления используют xxd -r без -p.

Восстановленные байты могут оказаться текстом, архивом или другим бинарным файлом. Если результат заранее неизвестен, удобно записать его в файл и проверить тип:
xxd -r dump.txt > restored
file restored
• printf '%s' передаёт строку как есть. Здесь в формате вывода нет \n, поэтому printf сам перенос строки не добавляет.
• | направляет вывод printf на вход xxd, как в прошлом задании с tr.
• xxd -r превращает шестнадцатеричную запись обратно в байты.
• -p означает, что на входе простой hex-текст. Каждая пара символов (4c, 69 и так далее) обозначает один байт.

### Расширение файла — подсказка, содержимое — проверка
Если file restored сообщает gzip compressed data, содержимое можно распаковать через gzip. Флаг -c отправляет результат в стандартный вывод, а перенаправление > записывает его в новый файл. Исходный файл при этом сохраняется.
| Что показывает `file` | Пример команды | Что происходит |
|---|---|---|
| `gzip compressed data` | `gzip -dc restored > unpacked` | Распаковывает данные в `unpacked` |
| `bzip2 compressed data` | `bzip2 -dc restored > unpacked` | Распаковывает данные в `unpacked` |
| `tar archive` | `tar -tf restored` | Показывает список файлов в архиве |
| `ASCII text` | `cat restored` | Выводит текст |
tar -tf unpacked. Флаг -t выводит список файлов внутри, а -f указывает имя архива.
Если файл упакован в несколько слоёв, после каждого шага снова запускай file для полученного файла. Например, после gzip может обнаружиться tar-архив, а внутри него — ещё один сжатый файл. Для таких упражнений удобно создать отдельный рабочий каталог командой mktemp -d.
• printf 'DevOps\n' выводит DevOps и перенос строки — тот самый байт 0a.
• | gzip передаёт вывод программе gzip, которая сжимает его.
• > payload записывает сжатые данные в файл с именем payload.
• file payload проверяет содержимое файла. Поскольку мы сжали его через gzip, ожидаем увидеть gzip compressed data, хотя у файла нет расширения.
• -d говорит gzip распаковать данные.
• -c отправляет распакованные данные в стандартный вывод. Исходный payload сохраняется.
• > unpacked записывает этот вывод в файл unpacked.
• file unpacked проверяет тип нового файла, а cat unpacked показывает его содержимое.
• tar -czf bundle.tar.gz payload создаёт архив из файла payload. Здесь -c создаёт архив, -t показывает список файлов в архиве. -z сжимает его через gzip, -x извлекает файлы в текущий каталог. а -f указывает, что следом идёт имя архива — bundle.tar.gz.
• gzip -dc bundle.tar.gz > bundle.tar снимает внешний слой gzip и записывает оставшийся tar-архив в bundle.tar.
• file bundle.tar проверяет, какой тип файла получился после распаковки.
• tar -tf bundle.tar показывает содержимое архива. -t выводит список файлов, а -f указывает имя архива. Ожидаем увидеть payload.

### SSH, TCP и TLS
Здесь пригодится то, что мы увидели с Nginx. 404 означал, что соединение состоялось и сервер прислал HTTP-ответ. При Failed to connect сбой происходил на этапе подключения. Сегодня добавим ещё один этап — согласование TLS.
| Инструмент | Что делает |
|---|---|
| `ssh -i ./key user@host` | Подключается по SSH и использует указанный приватный ключ для аутентификации |
| `nc localhost 30000` | Открывает TCP-соединение с локальной службой и передаёт ей ввод |
| `openssl s_client -connect localhost:30001` | Открывает TCP-соединение и пробует согласовать TLS с локальной службой |
Порты в примерах условные. Для SSH-файла с приватным ключом на своей ВМ можно выставить chmod 600 ./key: владелец сможет читать и записывать файл, остальные пользователи доступа к нему не получат.

Если nc подключился, ты подтвердил, что TCP-соединение открылось. Содержательный ответ зависит от того, какой протокол ожидает служба. Например, TLS-служба сначала ждёт TLS-рукопожатие, и обычная текстовая строка для неё будет некорректным началом обмена.
Чтобы проверить гипотезу о TLS, запусти openssl s_client -connect localhost:30001. Если клиент выведет согласованную версию TLS и набор шифров, рукопожатие состоялось.

nc -vz localhost 80
openssl s_client -connect localhost:80 </dev/null
• В первой команде nc пробует открыть TCP-соединение. -v показывает подробности, а -z проверяет подключение без отправки данных приложения.
• Во второй openssl s_client подключается к тому же порту и пытается провести TLS-рукопожатие. -connect задаёт адрес и порт, а </dev/null подаёт пустой ввод, чтобы команда не ждала текста с клавиатуры.

## cron и резервные копии

#!/usr/bin/env bash
shebang
.sh — это файл скрипта. Для него открой nano backup.sh

Строка backup_date=$(date +%F) сохраняет сегодняшнюю дату в переменную backup_date.
1. date +%F выводит дату в формате ГГГГ-ММ-ДД, например 2026-11-24.
2. $(...) говорит Bash выполнить команду внутри скобок и подставить её вывод.
3. backup_date=... сохраняет полученную строку в переменную. Вокруг = пробелов нет.
Здесь $(...) получает результат команды, а $backup_date подставляет уже сохранённое значение.

### Что такое cron
Cron — служба Linux, которая запускает команды по расписанию. Она работает в фоне. Терминал можно закрыть, а из SSH выйти. Главное, чтобы Ubuntu VM была включена и служба cron работала в момент запуска. Обычный cron пропускает запуск, если в назначенное время машина выключена.

Расписание пользователя называется crontab. Это список команд и времени их запуска.
| Команда | Что делает |
|---|---|
| `systemctl is-active cron` | Показывает, работает ли служба сейчас |
| `crontab -l` | Показывает расписание текущего пользователя |
| `crontab -e` | Открывает расписание текущего пользователя для редактирования |
Ты уже видел cron is active в практике с check-service.sh. Это означает, что служба работает. Чтобы узнать, какие задания ей поручены от твоего имени, нужна отдельная команда crontab -l.

### Как читать расписание
В пользовательском crontab у каждой записи пять полей времени, после них идёт команда.
| Поле | Допустимые значения |
|---|---|
| Минута | `0–59` |
| Час | `0–23` |
| День месяца | `1–31` |
| Месяц | `1–12` |
| День недели | `0–7`, где `0` и `7` — воскресенье |

Звёздочка * означает «любое значение в этом поле».
0 2 * * * /usr/bin/bash /home/alex/study/week4/mon/backup.sh
Читай слева направо. Минута 0, час 2, любой день месяца, любой месяц, любой день недели. Получается каждый день в 02:00 по времени Ubuntu VM. Её текущее время можно посмотреть командой date.

| Расписание | Когда запустится |
|---|---|
| `* * * * *` | Каждую минуту |
| `*/5 * * * *` | Каждые пять минут |
| `30 18 * * 1` | Каждый понедельник в 18:30 |
| `0 2 * * *` | Каждый день в 02:00 |

При проверке удобно временно поставить запуск каждую минуту. Когда убедимся, что задание работает, установим ночное расписание.

### Почему скрипт может работать вручную и падать в cron
Когда ты запускал bash check-nginx.sh, ты уже находился в ~/study/week4/mon. Поэтому путь ./check-service.sh указывал на нужный файл. При запуске по расписанию cron не наследует папку, которую ты открыл в терминале. Команда ./check-service.sh по-прежнему означает «найди файл в текущей папке», но текущая папка может быть другой.

Поэтому в расписании укажем абсолютный путь к backup.sh, а внутри скрипта зададим пути к исходной папке и архиву. Ещё у cron может быть более короткий PATH — список папок, в которых оболочка ищет команды. В примере мы явно указали /usr/bin/bash.

### Что будет делать backup.sh
Скрипт должен создать архив учебной папки и добавить дату в его имя. Для этого пригодятся две команды.
backup_date=$(date +%F)
Запись $(...) запускает команду и подставляет её текстовый вывод. Здесь date +%F выдаёт дату в формате ГГГГ-ММ-ДД, а Bash сохраняет её в переменную backup_date. Ты уже знаешь похожие записи. "$backup_date" подставляет значение переменной, а $? содержит код завершения последней команды.

Сам архив создаёт tar. Ниже пример для случая, когда папка /home/alex/study-backups уже создана.
tar -czf "/home/alex/study-backups/week4-$backup_date.tar.gz" \
    -C /home/alex/study week4

Здесь -c создаёт архив, -z сжимает его через gzip, а -f указывает имя файла архива. -C /home/alex/study говорит tar, откуда взять папку week4. Архив хранится отдельно от исходной папки, поэтому следующий запуск не захватит предыдущие архивы.

Как и в check-service.sh, можно поместить команду прямо в if. Если tar вернул 0, скрипт напечатает сообщение об успехе. Если код ненулевой, скрипт сообщит об ошибке и сам завершится с ненулевым кодом.

### Куда пойдёт вывод ночного задания
У задания cron нет открытого терминала, в который ты сможешь посмотреть утром. Поэтому запишем обычный вывод и ошибки в один файл.
0 2 * * * /usr/bin/bash /home/alex/study/week4/mon/backup.sh >> /home/alex/backup.log 2>&1
Bash обрабатывает перенаправления слева направо. Сначала >> направляет stdout в backup.log и дописывает новые строки в конец файла. Затем 2>&1 направляет stderr туда же, куда уже направили stdout. Это те же два потока, которые ты проверял с active.txt и usage.txt.

Утром tail -n 20 /home/alex/backup.log покажет последние сообщения скрипта, а tar -tzf имя-архива.tar.gz позволит посмотреть содержимое архива без распаковки.

## Bash и автоматическая очистка старых бэкапов
### Зачем бэкапам срок хранения
Твой скрипт каждую ночь создаёт архив в ~/study-backups. Если архив занимает 100 МБ, за неделю накопится около 700 МБ, а за 30 дней — около 3 ГБ. Чтобы папка не росла бесконечно, задают срок хранения. В нашем случае после успешного создания архива скрипт ищет старые копии и удаляет их.

Есть два разных правила хранения. «Хранить архивы за последние семь суток» означает отбирать файлы по возрасту. «Хранить семь последних архивов» означает отбирать их по количеству. Если два ночных запуска пропущены, по первому правилу файлов может остаться пять. Твой план задаёт правило по возрасту.

### Как find отбирает файлы
Начнём с команды, которая выводит список кандидатов на удаление:
find "$HOME/study-backups" -maxdepth 1 -type f -name '*.tar.gz' -mtime +6 -print

| Часть команды | Что она делает |
|---|---|
| `"$HOME/study-backups"` | Ищет в папке, куда твой скрипт складывает архивы |
| `-maxdepth 1` | Проверяет файлы непосредственно в этой папке, без обхода подпапок |
| `-type f` | Отбирает обычные файлы |
| `-name '*.tar.gz'` | Отбирает имена, заканчивающиеся на `.tar.gz`. Кавычки передают шаблон самой команде `find` |
| `-mtime +6` | Отбирает файлы, с последнего изменения которых прошло минимум семь полных суток |
| `-print` | Печатает пути к найденным файлам |

Если в папке лежат архивы разных проектов, шаблон имени стоит сузить до префикса, который использует твой backup.sh. Тогда очистка затронет только архивы этого скрипта.

### Почему -mtime +6 означает семь суток
find считает возраст файла по времени последнего изменения его содержимого. Он делит прошедшее время на 24 часа и округляет вниз. Запись +6 означает «целое число прошедших суток больше шести». Поэтому -mtime +6 срабатывает с семи полных суток, а -mtime +7 — с восьми. Дата в имени архива в этом сравнении не участвует.

| Возраст файла | Полных суток | `-mtime +6` | `-mtime +7` |
|---|---:|---|---|
| 6 суток 23 часа | 6 | Пропустит | Пропустит |
| 7 суток 1 час | 7 | Выберет | Пропустит |
| 8 суток 1 час | 8 | Выберет | Выберет |

Скрипт проверяет возраст во время ночного запуска. Если файлу исполнилось семь суток днём, в список он попадёт при следующей проверке.

### Как связать создание архива и очистку
У тебя уже есть проверка успешности tar. Очистку помещаем в ветку успешного создания архива. Если исходная папка пропала, как в твоём тесте с backup-fail.sh, скрипт запишет Backup failed, вернёт 1 и сохранит прежние копии.

В Bash команда внутри if сама даёт результат проверки. Код 0 ведёт в then, ненулевой код — в else. Так можно проверить и создание архива, и очистку. Если tar отработал, а find сообщил об ошибке, в лог стоит вывести оба факта: архив создан, очистка завершилась с ошибкой.

Для предварительной проверки используется -print. После проверки списка действие -delete удаляет совпавшие файлы. Условие по возрасту, расширению и папке в обоих случаях одинаковое. gnu.org

### Что покажет ночной лог
Твоя запись в crontab уже направляет обычный вывод и ошибки в backup.log через >> ... 2>&1. Если скрипт сообщает об итогах каждого этапа, по логу можно различить три ситуации:

| Ситуация | Что записать в лог |
|---|---|
| Архив создан, очистка прошла | Путь к новому архиву и результат очистки |
| Архив создан, при очистке возникла ошибка | Путь к новому архиву и сообщение об ошибке очистки |
| `tar` завершился с ошибкой | Сообщение об ошибке создания архива |

Пустой вывод от find ... -print при успешном выполнении означает, что подходящих старых файлов пока нет. Для свежей папки с бэкапами это обычный результат.

## Автоматический бэкап с очисткой и проверкой
### Как cron выбирает скрипт
Cron запускает команду, записанную в crontab. В твоём случае запись выглядит примерно так:
0 2 * * * /usr/bin/bash /home/alex/study/week4/tue/backup.sh >> /home/alex/backup.log 2>&1
Если там указан ~/study/week4/tue/backup.sh через его абсолютный путь, правки в wed/backup-cleanup.sh на ночной запуск не повлияют.

• 0 2 * * * задаёт ежедневный запуск в 02:00 по времени планировщика. На твоей VM это UTC.
• /usr/bin/bash /home/alex/study/week4/tue/backup.sh указывает, какой именно файл выполнит Bash. Изменения в wed/backup-cleanup.sh попадут в ночной запуск только после того, как ты перенесёшь их в tue/backup.sh или укажешь путь к новому файлу в crontab.
• >> /home/alex/backup.log дописывает обычный вывод в конец лога. 2>&1 направляет туда же ошибки.

crontab -l показывает, что запланировано. По логу и состоянию файлов можно проверить, что выполнилось.

Команда показывает записи cron твоего пользователя. В нужной строке нас будут интересовать три вещи: время запуска, путь к скрипту и путь к логу. Именно этот скрипт и этот лог мы будем проверять.

### В каком порядке должен работать backup.sh
1. Создать каталог назначения, если его ещё нет.
2. Создать архив исходной папки с датой в имени.
3. Проверить код завершения tar. При ошибке записать сообщение в stderr и завершить скрипт с ненулевым кодом.
4. После успешной архивации выполнить очистку. В твоём учебном варианте find ищет только обычные файлы в верхнем уровне каталога, с именем backup-demo-*.tar.gz и возрастом от семи полных суток.
5. Записать результат. Если архив создан, но очистка завершилась ошибкой, лог должен отразить оба факта.

| Шаг | Что делает скрипт | Что делать при ошибке |
|---|---|---|
| 1. Создание | `tar` создаёт архив | Записать ошибку в лог, завершиться с ненулевым кодом и сохранить старые копии |
| 2. Проверка | `tar -tzf` читает архив и выводит список файлов | Записать ошибку и сохранить старые копии |
| 3. Очистка | `find` удаляет подходящие архивы возрастом от семи полных суток | Записать, что очистка завершилась ошибкой |

Для очистки пригодится вчерашнее условие:
find "$backup_dir" -maxdepth 1 -type f -name 'backup-demo-*.tar.gz' -mtime +6 -print
Здесь -print показывает кандидатов на удаление. Когда убедимся, что список правильный, используем -delete в скрипте. Вчера ты уже проверил важную деталь: -mtime +6 выбирает файлы от семи полных суток, а -mtime +7 — от восьми.
Ещё один случай, который стоит учесть: имя архива содержит только дату, поэтому два запуска за день могут писать по одному пути. Если второй запуск оборвётся, он может испортить уже готовую копию. Чтобы её сохранить, можно сначала создать архив под временным именем в той же папке, проверить его и только потом переименовать в итоговый файл.


Представь, что исходную папку переименовали. tar завершится ошибкой, и нового пригодного архива у тебя не будет. Поэтому скрипт должен остановиться до очистки. В прошлый раз ты уже подтвердил это вручную. Теперь тот же порядок должен выполняться в файле, который запускает cron.

Ещё одна деталь про имя архива. Если в нём только дата, ручной запуск и запуск по расписанию в одни сутки пишут в один и тот же файл. Сам факт, что архив существует, не доказывает, что его создал cron. Для этого пригодятся время изменения файла и свежая запись в логе.

### Как проверить автоматический запуск
| Что проверяем | Какое доказательство ищем |
|---|---|
| Cron запускает нужный файл | В `crontab -l` указан путь к итоговому `backup.sh` |
| Скрипт действительно выполнился по расписанию | В логе появилась свежая запись с ожидаемым временем |
| Скрипт записал архив | Время изменения архива совпадает с запуском, а `tar -tzf` показывает ожидаемые файлы |
| Очистка отработала | Подходящий старый тестовый архив исчез, свежий архив остался |
| Из архива можно вернуть данные | После распаковки в отдельную папку `diff` подтверждает, что контрольный файл совпадает с исходным |

У этих проверок разные задачи. bash -n backup.sh проверяет синтаксис, tar -tzf показывает содержимое архива, а распаковка и diff проверяют восстановление. Для проверки восстановления используем tar -xzf … -C … с отдельной папкой, как на прошлом занятии. Затем cmp сравнит восстановленный файл с исходником. Если файлы одинаковые, cmp обычно ничего не печатает и возвращает 0.

Чтобы проверить цепочку без ожидания ночи, на практике можно на короткое время запланировать запуск на ближайшую минуту с учебным каталогом, посмотреть результат и вернуть расписание на 02:00 UTC.

### Зачем нужен лог
Ты уже использовал запись такого вида:
«>> /полный/путь/backup.log 2>&1

«>> дописывает стандартный вывод в конец лога. 2>&1 отправляет туда же сообщения об ошибках. Если скрипт пишет время запуска и результат каждого этапа, утром по логу можно понять, запускался ли он, был ли создан архив и дошло ли дело до очистки.
